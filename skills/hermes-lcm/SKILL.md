# Hermes-LCM

Use this skill when a task concerns Hermes-LCM setup, operation, compaction, diagnostics, session behavior, or recall from compacted and cross-conversation history.

Start here:

1. Confirm that the `hermes-lcm` plugin is enabled and `context.engine` is `lcm`.
2. For exact historical claims, use the recall workflow instead of trusting a compacted summary.
3. Use `lcm_status`, `lcm_inspect`, and `lcm_doctor` before changing configuration or attempting repair.
4. Treat slash-command apply paths as mutations: preview first, keep backups, and require the user's authorization.
5. Load the relevant reference rather than guessing arguments or lifecycle semantics.

Working rules:

- Raw stored messages are authoritative; summaries are bounded recall cues.
- Prefer newer source-backed evidence when it conflicts with an older summary.
- Start with the narrowest useful scope and expand only when exact detail is needed.
- Do not infer exact commands, paths, timestamps, values, counts, or causal chains from summaries alone.
- Keep current-session, cross-conversation, and Hermes history outside `lcm.db` distinct.
- Do not treat open-cardinality results as complete without product-verifiable enumeration or coverage.
- Use `lcm_compile_evidence` when a historical answer needs several named facets, exact operands, conflict handling, or latest-state selection; treat its semantic proposal as untrusted until the product returns validated evidence.
- Keep default-off assertion, query-view, adaptive-retrieval, and destructive operator paths default-off unless the user explicitly asks to enable them.

Diagnostic rules (learned from live incidents):

- **`degraded_reason: "semantic vectors are unavailable (coverage=none)"` is NOT evidence the vectors are gone — but it is NOT automatically benign either. There are TWO causes and they look identical from the flag alone.** (a) Benign: the semantic arm scopes to the CURRENT session, which has no summary nodes until its first compaction (default threshold 35% of the context window), so a fresh, long session degrades to full-text by design. (b) Real: the backfill has not run, so the store genuinely lacks vectors for recent history — measured 2026-09-16, the last vector was 3 days old, coverage was ~10% of the store, and `remaining: 0` had not been reached since the one manual run. **Distinguish them by the GLOBAL row counts, never by the session-scoped flag:** compare `count(*)` of `lcm_chunk_meta` / `lcm_embedding_meta` against the eligible messages, and check `max(embedded_at)` — a date days in the past means (b), not (a). Also verify the provider end-to-end (a live POST to the configured endpoint) before blaming the store.
- **Embeddings are NOT created automatically on ingest.** Coverage is populated by the manual `/lcm embed backfill --corpus both --apply`, so a store that is never backfilled keeps growing while its vector coverage stays frozen — silently. If semantic recall matters, put the backfill on a schedule; one manual run is a patch, not a fix. The flag to watch is `coverage` on a `lcm_grep(mode='semantic')` result: `coverage: "full"` + `degraded_to_fts: false` is the healthy state.
- **`remaining: 0` does NOT mean every message is embedded — check the eligibility rules before reporting a shortfall.** The `conversational` policy skips `tool` output entirely and `chunking.py` drops conversational turns under `_MIN_CONVERSATIONAL_TOKENS = 40`. Measured after a COMPLETE backfill: 16 920 of 114 305 messages covered (~15%), yet zero *long* (>=200 char) eligible messages were missing — the gap was entirely tool rows, empty tool-only turns, and sub-40-token replies. Report coverage against the eligible set, not against `count(*) FROM messages`.
- **A cron job cannot pass arguments to its script** (`_run_job_script` builds `argv = [python, <path>]`, `scheduler_script.py`), and `/lcm …` is a chat command, not a CLI subcommand — there is no `hermes lcm`. To run a slash-command action on a schedule, write a script that imports the plugin the way the gateway does and calls `command.handle_lcm_command("<args>", engine)` directly; make the **argument-less invocation the safe default** so the cron tick works with no argv.
- **Any second process that opens the live `lcm.db` is the #588/#597 trigger** — including a backfill script. Gate such a script on the lockfix patch being active (probe the wrapped attribute, not `hermes plugins list`) and refuse to run without it. The gate probe must use the RIGHT ORDER: load the lockfix plugin first (its `register(ctx=None)` installs the meta-path import hook), THEN `import sqlite_util` from the plugin dir — sqlite_util imports UNPATCHED when imported before the finder is installed, and a plain `sys.path` import under the bare module name `sqlite_util` still gets patched because the finder matches on the file path (`_PLUGIN_DIR_MARKER = "hermes-lcm"`), not the module name. Verify with `hasattr(sqlite_util._chmod_sqlite_artifact_at, '__wrapped__')`.
- **Standalone backfill script recipe (verified live):** the gateway imports dir plugins as `hermes_plugins.<slug>` via a synthetic parent package — reproduce it with `spec_from_file_location('hermes_plugins.hermes_lcm', '<plugin>/__init__.py', submodule_search_locations=['<plugin>'])`, seed `sys.modules['hermes_plugins']` (a bare module with `path=[<plugins_dir>]`) and `sys.modules['hermes_plugins.hermes_lcm']` BEFORE `exec_module`; then `import hermes_plugins.hermes_lcm.command` / `.engine` works. Build the engine with `LCMEngine(hermes_home='/opt/data')` (config comes from env), and call `lcm_command.handle_lcm_command('<args>', engine)` — signature `(raw_args: str | None, engine)`.
- **A backfill apply round can report `selected: 0, pending: 0` with `remaining` stuck at a nonzero number when stale `lcm_embedding_backfill_inflight` rows reference chunk ids that no longer exist under the active identity.** Mechanism: re-chunking after new content is re-ingested can produce FEWER chunks than the failed attempt (the old third chunk `:2` disappears), so the `NOT EXISTS` selector excludes every in-flight id and pending collapses to 0 — `--retry-uncertain` also selects nothing because `_chunk_authorized_uncertain_rows` excludes inflight ids whose chunks already exist (a NULL LEFT JOIN on the same condition). Diagnose with a LEFT JOIN of inflight against `lcm_chunk_meta` on `chunk_id = embedded_id`: a NULL join for a `state='uncertain'` row is a dead marker. Delete dead markers directly ONLY after proving per the checklist in the next bullet (zero rows in every vector/meta/binary table, the store re-embedded under the active identity after the failure, no triggers/FKs, verified backup) — after deletion the dry-run immediately shows the real pending count and the loop progresses.
- **A `lcm_embedding_backfill_inflight` row in state `uncertain` is durable by design** — never silently resent, only re-dispatched by an explicit `/lcm embed backfill --apply --retry-uncertain`. That command RE-SENDS to the provider; it does not purge. When an embedding identity is superseded (`active=1` → `active=0`), its stuck markers have no operator path at all and accumulate forever. Delete them directly only after proving: the identity owns zero rows in every vector/meta/binary table, every `embedded_id` is already embedded under the active identity (so recall coverage is unchanged), the table has no foreign keys or triggers, and a verified backup exists.
- **This skill is a symlink into the plugin** (`/opt/data/skills/hermes-lcm -> /opt/data/plugins/hermes-lcm/skills/hermes-lcm`), so `skill_manage` cannot patch it — it reports "not found in active profile". Edit the file at the resolved path directly.
- **MEASURED 2026-09-19 — our compaction cost is 99.6% LLM call, and the local half is sub-millisecond.** 118 real compactions from `agent.log`/`gateway.log` (2026-08-25 → 2026-09-19). **Timing:** median **30.6 s**, mean 46.3 s, min 8.4 s, max 219.0 s. **Reduction on the same 105 paired runs: median 58.8%, range 26.7–95.4%**. **Where the time goes:** the auxiliary summarizer call (`deepseek-v4-flash`) has median latency **11.8 s** and is the dominant cost; every local retrieval operation is sub-millisecond — `lcm_grep` FTS 0.13 ms, exact phrase 0.64 ms, reading a single message 0.01 ms, restoring a whole 125-source node 0.17–0.28 ms, DAG listing 0.12 ms, `nodes_fts` 0.04 ms (median of 9, on a copy of the live 149 697-message DB). **So do not describe LCM as slow:** the local engine is ~5 orders of magnitude faster than the model call, and the model call is the part every LLM-summarizing engine pays.
- **Our reduction figure is bimodal — always quote the distribution, never a single number.** Measured 2026-09-19 across 105 paired compactions: **58.8% median**, but the spread runs 26.7%–95.4%. Two regimes. *Fresh backlog* (a large backlog accumulated since the last compaction) crushes hard — 821 msgs → 33 at 93.0%, 834 → 34 at 92.8%, 965 → 34 at 94.4%. *Steady-state top-ups* (a small new batch) barely reduce — 61 msgs → 34 at 40.2%, 60 → 33 at 46.6%, 77 → 33 at 38.9%. A low percentage is NOT a failure or a misconfiguration: it is the small-batch regime, where the fixed cost of a summary frontier dominates. Judge a single compaction by which regime it is in.
- **Reduction and speed trade off, and it is visible per run.** Measured 2026-09-19: 95.4% reduction took 145.9 s while 71.1% took 44.5 s. Do not promise both a deeper squeeze and a faster pass.
- **Quote third-party numbers only with their axis attached.** External Hermes compaction plugins (2026-09-19) report 75% vs 55% reduction and 5.6 s vs 44.8 s on **~75k-token snapshots, per compaction**. Our 58.8% median is the same axis (per-compaction, token before/after) and IS comparable; our `lcm_status` DAG ratio (98%, corpus-scale) is NOT. State which one is being quoted.
- **A reduced context is out of distribution — the risk applies to us too.** Raised 2026-09-19 by a plugin author's reviewer and left unmeasured: an agent sees a compacted transcript unlike anything it was trained on, and no one in that thread had data on the effect. When evaluating recall quality after compaction, prefer tasks that need the compacted region rather than the fresh tail.
- **Measure on a BACKUP, never the live DB.** The 2026-09-19 benchmark used `sqlite3.Connection.backup()` into `/tmp` (667 MB, `quick_check: ok`, 149 697 messages) — a second process opening the live `lcm.db` is the #588/#597 trigger. Verify the copy before trusting its numbers, and delete it afterwards.
- **A second process CAN safely touch lcm.db** — the POSIX-lock fix (early return on already-0600 artifacts + O_PATH chmod via `/proc/self/fd`) now ships NATIVELY in the fork's `sqlite_util.py`; the import-hook gate from the retired `00-lcm-lockfix` plugin is no longer needed. A standalone backfill importing `engine.py` directly still hits relative-import errors — load the plugin as a package: synthesize `sys.modules['hermes_plugins']` (bare module, `path=[<plugins_dir>]`), then `spec_from_file_location('hermes_plugins.hermes_lcm', '<plugin>/__init__.py', submodule_search_locations=[...])` with `m.__path__ = ['<plugin>']` set BEFORE `exec_module`, then `import hermes_plugins.hermes_lcm.engine`. Set LCM_* env defaults explicitly in the script (`os.environ.setdefault`) — a standalone process does not inherit the gateway's container env, and without them the backfill is refused with 'embeddings are disabled'.
- **Backfill-loop tool functions need exact kwargs**: `_lcm_grep_embed_query(provider, query, *, remaining_s)` (provider positional first, remaining_s keyword-only); `run_knn(..., vector_store_cls=tools.VectorStore, provider=<resolved provider OBJECT> from tools._lcm_grep_resolve_provider(engine) — a string is rejected with AttributeError 'model_id'; engine positional FIRST, query-vector as kw — passing the args-dict as first positional fails 'multiple values for engine'); results come back as a LIST of KNNResult objects, not a JSON dict — never json.loads it; a zero query vector is rejected by `_normalized` (embed a real query). The `lcm_grep`/`lcm_recall` tool fns take their arguments as a single DICT first positional (`{'query': ..., 'mode': ..., 'session_scope': ...}`, `engine=engine` kw) — a positional string fails `args.get`. Valid session_scope values: `current`, `all`, `session`; anything else is silently ignored with an `ignored_session_scope` note.
- **`coverage=none` on the AGENT-session `lcm_grep(semantic)` after a full backfill is the benign session-scope case (a)**: the semantic arm scopes to the current session's summary nodes; a session with zero compactions has none by design. The GLOBAL corpus is what the backfill fills — verify with a standalone `run_knn` (conversation_ids=None) → `coverage: full`, hits returned. After the 2026-09-26 backfill: chunk corpus 37 256/37 256, summary embeddings 99 = ALL depth-0 leaf nodes (depth-1/2 are intermediate DAG layers, not embedded by design — verified: embedded-by-depth = 99×depth0 only).
- **A killed/timed-out backfill run holds the lease for TTL=600s (10 min) — subsequent runs refuse with "another embedding backfill holds the lease".** The lock survives the process (row in lcm.db, not a process lock): killing or timing-out a run does NOT free it. For scripted catch-up loops, run each round to completion (batch is only 200 chunks / ~50 s per round) and never kill mid-round; if you must, set env `LCM_EMBEDDING_BACKFILL_LEASE_TTL_S` low (e.g. 60) on ALL runs of the batch — it must match across rounds (compare-and-swap on owner id).
- **A standalone script must self-provide the LCM_* env (`os.environ.setdefault`) — a process outside the gateway (cron, kernel, shell) does NOT inherit the gateway's container env, and the backfill refuses with "embeddings are disabled" even when the gateway itself works fine.** Set at minimum: LCM_EMBEDDINGS_ENABLED, LCM_EMBEDDING_PROVIDER, LCM_EMBEDDING_MODEL, LCM_OLLAMA_BASE_URL (our values live in the compose service `environment:`, mirror them in the script header).
- **Cron `--script` paths are relative to `/opt/data/scripts/` — absolute paths are REFUSED.** Place the script there and pass the bare filename; the same script under `/opt/data/work/` will not create a job.
- **Dead inflight markers block chunk selection silently**: rows in `lcm_embedding_backfill_inflight` whose `embedded_id` (chunk_id like `199306:2`) no longer exists under the active identity (re-chunking produced fewer chunks) keep `pending: 0, selected: 0` forever with `in_flight: N`. Deletion criteria (all verified before the 09-26 delete): zero rows in vector/meta/binary for the id, the parent store already re-embedded under the active identity, no triggers/FKs, verified backup. After deletion the backfill resumes immediately.
